rPBFT

rPBFT: Reliable Practical Byzantine Fault Tolerance Mechanism for Faulty Distributed Networks

일부 노드에 지연이나 장애가 생겨도 거래 합의 성능을 유지하는 합의 구조를 설계하고 비교했습니다.

역할
공동 제1저자
게재
IEEE Transactions on Big Data, Vol. 12, No. 3, pp. 814–828, 2026
지표
SCIE, IF 5.7, Q1, JCR Top 11.9%

개요

응답 지연과 메시지 유효성으로 노드 상태를 갱신해 합의 그룹을 구성하는 rPBFT를 설계했습니다.

역할

공동 제1저자로 기존 개선안을 비교하고 최대 1,000노드 시뮬레이터로 정상과 장애 환경을 평가했습니다.

성과

장애 환경에서 지연과 처리량을 개선했고 IEEE Transactions on Big Data에 게재됐습니다.

지연시간 감소

50~80%

문제

내용

참여 노드가 늘거나 일부가 고장 나면 블록체인의 거래 확정이 느려집니다.

상황
금융기관이 원장을 공동 관리하려면 여러 노드가 같은 거래 순서에 합의해야 합니다.
기존 방식
PBFT 합의는 노드가 늘수록 메시지가 제곱으로 늘고 고장 난 노드가 지연을 키웁니다.

접근

내용

최근 정상 참여 이력이 좋은 노드로 합의 그룹을 구성하는 rPBFT를 설계했습니다.

노드 상태
메시지 유효성과 응답 지연으로 노드 상태를 갱신하고 회복한 노드는 다시 참여시킵니다.
평가 방법
Python 기반 비동기 네트워크 시뮬레이터로 최대 1,000노드까지 PBFT, HotStuff와 비교했습니다.
역할
공동 제1저자로 기존 개선안의 한계를 비교하고 정상과 장애 환경의 성능을 나눠 평가했습니다.

결과

내용

장애 조건에서 지연시간은 30~40% 감소했고 처리량은 50~80% 향상되었습니다.

성공률
합의 성공률은 33% 향상되었습니다.
메시지 수
1,000노드, 500거래의 장애 조건에서 PBFT 약 2,933만 건, rPBFT 약 316만 건이었습니다.
게재
IEEE Transactions on Big Data(SCIE, JCR 상위 11.9%)에 게재됐습니다.

한계와 다음

내용

정상 환경에서는 노드 상태 계산 비용 때문에 PBFT보다 항상 효율적이지 않았습니다.

악의적 노드
악의적 노드가 약 28~30%를 넘으면 합의 그룹의 정직한 다수가 무너져 합의가 멈췄습니다.
다음
시뮬레이터 평가이므로 실제 네트워크 검증과 설정값 자동 조정이 필요합니다.

실무 활용

내용

외부 블록체인 인프라를 검토할 때 장애 상황의 성능을 확인하는 데 쓸 수 있습니다.

활용 장면
금융기관용 네트워크에서 일부 노드 장애로 거래 확정 시간이 늘 수 있을 때입니다.
활용 방법
제시된 성능 수치를 실제 노드 규모와 장애 조건에서 다시 비교하고 늘어나는 통신량과 자원도 함께 봅니다.
주의할 점
시뮬레이터에서 얻은 결과이며 한화금융 환경에 적용한 결과는 아닙니다.
작업 기록 전체 보기
기술 스택
Python 3.10.1 / asynchronous network simulator / PBFT / HotStuff / rPBFT comparative implementation / Weibull / exponential / lognormal reliability models / message digest verification / latency, throughput, success-rate metrics
해결해야 한 문제
노드가 늘거나 일부가 고장 나면 PBFT의 합의가 느려집니다. 블록체인 기반 금융 서비스는 중앙 관리자가 없어도 여러 노드가 거래 순서와 원장 상태에 합의해야 합니다. 거래 확정이 빠르고 일관성이 있지만 노드 수가 늘수록 메시지가 제곱으로 증가합니다. 느리거나 일시적으로 고장 난 노드는 합의 지연과 재전송을 키웁니다. 악의적 노드나 고정 점수에 집중해 자연 고장의 회복 과정을 충분히 반영하지 못했습니다.
왜 이 문제였나
실제 분산 시스템에서는 악의 없는 고장이 반복되기 때문입니다. 하드웨어 노후화, 초기 불량, 통신 지연과 패킷 손실처럼 비악의적이고 확률적인 장애가 반복됩니다. 정상 상태의 최고 처리량만 비교하면 이런 환경에서 운영 연속성을 판단하기 어렵습니다.
목표
장애 환경에서 지연, 처리량, 합의 성공률을 함께 개선하는 것이 목표였습니다. 각 노드의 메시지 유효성과 지연을 이용해 신뢰도를 갱신합니다. 신뢰도가 높은 노드로 합의 그룹을 동적으로 구성합니다.
검토한 방법
최근 PBFT 개선 연구를 네 계열로 분류해 한계를 비교했습니다. 대표 노드 중심, 계층형, 점수 기반, 소규모 합의 그룹 방식의 네 계열입니다. 대표 노드가 병목이 되는 구조와 낮은 점수를 받은 노드의 영구 배제를 비교했습니다. 소규모 그룹의 보안 약화와 별도 검증 비용도 비교했습니다.
선택한 방법
대표자 없이 모든 노드가 같은 합의 그룹을 계산하는 구조를 선택했습니다. 단일 대표자를 선출하지 않고 각 노드가 동일한 입력으로 같은 합의 그룹을 계산합니다. 노드 상태 점수(FSI)에 감쇠와 패널티, 보상을 적용해 일시적 장애 노드가 회복할 수 있게 했습니다. 합의 메시지를 전체 노드 n이 아니라 합의 그룹 c에 집중해 복잡도를 O(n²)에서 O(c²)로 줄였습니다.
구현
최대 1,000노드 규모의 합의 시뮬레이터를 구현해 세 방식을 같은 지표로 비교했습니다. 최대 1,000노드의 완전 연결 네트워크에서 비동기 메시지 지연을 반영한 합의 시뮬레이터를 구현했습니다. 합의 메시지의 유효성과 지연을 노드 상태로 기록했습니다. 최근 이력과 네트워크 거리를 사용해 합의 그룹을 재구성했습니다. 초기 고장, 무작위 고장, 마모 고장을 욕조 곡선으로 조합했습니다. PBFT, HotStuff, rPBFT를 정상과 장애 조건에서 같은 지표로 비교했습니다.
어려움
정상 환경의 추가 비용과 장애 환경의 회복 효과를 한 수치로 설명할 수 없었습니다. 합의 그룹을 줄이면 통신량은 줄지만 신뢰도 계산과 재구성 자체가 비용입니다. 합의 그룹이 작으면 장애 노드의 영향이 커집니다.
해결
조건을 나누고 여러 지표를 함께 측정해 비교했습니다. 노드 수와 블록 수, 장애 비율과 부하를 나눠 100회 반복 평균을 비교했습니다. 지연과 처리량뿐 아니라 합의 성공률, 메시지 수, CPU와 메모리, 네트워크 사용량을 함께 측정했습니다. 합의 그룹 크기와 감쇠계수도 네트워크 규모별 범위로 제시했습니다.
정량 결과
장애 조건에서 지연시간은 30~40% 줄고 처리량은 50~80% 늘었습니다. PBFT와 HotStuff입니다. 장애 조건에서 지연시간 30~40% 감소, 처리량 50~80% 향상, 합의 성공률 33% 향상을 확인했습니다. 1,000노드, 500거래의 장애 조건에서 PBFT 약 2,933만 건, rPBFT 약 316만 건이었습니다. 네트워크 장애 비율 60%까지는 상대적으로 안정적인 처리량을 유지했습니다. 하지만 악의적 노드가 약 30%를 넘으면 합의 그룹의 정직한 다수가 무너지며 합의가 붕괴했습니다.
목표 달성
장애 환경에서는 목표를 달성했지만 정상 환경에서는 PBFT보다 항상 낫지는 않았습니다. 모델링한 장애 환경에서는 지연과 처리량, 합의 유지 측면의 목표를 달성했습니다. 정상 환경에서는 노드 상태 계산과 합의 그룹 관리 비용 때문에 PBFT보다 항상 우수하지 않았습니다.
기여
정상과 장애 환경을 나눠 성능과 비용의 교환관계를 명시했습니다. 공동 제1저자로 논문의 문제 전개와 비교 평가 범위를 함께 정교화했습니다. 정상과 장애 환경을 구분하고 성능, 내결함성, 자원 비용의 교환관계를 명시했습니다.
배운 점
인프라는 평균 처리량보다 어떤 장애를 가정했는지로 평가해야 한다는 점을 배웠습니다. 어떤 장애를 가정하고 어느 구간에서 회복력을 확보하는지로 인프라를 평가해야 합니다. 가장 낮은 메시지 수와 가장 낮은 지연이 같은 설계에서 나오지 않는다는 점도 확인했습니다.
한계
Python 시뮬레이터와 악의 없는 장애에 집중한 평가입니다. Python 시뮬레이터와 확률적이고 비악의적인 장애에 집중했습니다. 가짜 노드를 대량으로 만드는 공격(Sybil), 조직적 서비스 거부 공격, 합의 그룹 담합, 노드 상태 위조에 대한 대규모 실증은 제한적입니다. 합의 그룹 크기와 감쇠계수는 경험적으로 정했습니다.
후속 연구
실제 네트워크에서의 검증과 설정값 자동 조정이 필요합니다. 클라우드 테스트 네트워크에서 공격 시나리오와 수천 노드의 수렴 비용, 공간 비용을 검증해야 합니다. 네트워크 상태에 따라 합의 그룹 크기와 감쇠계수를 자동 조정하는 방법이 필요합니다.
조직에서 내리는 판단
금융기관용 블록체인 네트워크와 디지털자산 플랫폼은 여러 기관과 외부 기술이 연결되기 때문에 처리 속도가 높더라도 일부 노드 장애나 통신 지연이 생기면 거래 확정 시간이 늘고 운영 부담이 커질 수 있습니다. 특히 외부 인프라나 파트너 기술을 검토할 때는 제시된 성능 수치보다 실제 서비스의 노드 규모, 거래량, 장애 조건에서 성능이 어떻게 달라지는지 확인하는 과정이 필요합니다. rPBFT에서는 노드 수와 장애 조건을 직접 바꿔가며 성능이 유지되는 구간과 추가 비용이 커지는 구간을 비교했습니다. 여러 합의 구조를 직접 구현하고 조건을 바꿔가며 비교해본 만큼, 외부 블록체인 인프라를 검토할 때도 어떤 조건에서 성능이 달라지고 운영 부담이 커지는지 구체적으로 볼 수 있습니다. 한화금융 환경에 직접 적용한 결과는 아닙니다.
