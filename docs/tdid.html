T-DID

T-DID: Runtime Security Information and Stateful Threat Adjudication for DID/VC Systems

디지털 신원(DID) 표준이 보안 점검에 필요한 기록을 정하지 않는다는 문제에서 출발해, 표준과 공개 구현체에서 위협과 필요한 보안 정보를 식별하고 공통 보안 이벤트 스키마와 런타임 판정 구조를 설계했습니다.

상태
원고 마무리 단계, 투고 준비 중

개요

디지털 신원 표준과 공개 구현체에서 위협 21개와 점검에 필요한 보안 정보를 식별하고, 공통 보안 이벤트 스키마와 이를 쓰는 런타임 판정 프로토타입 T-DID를 구현했습니다.

역할

4인 연구팀의 팀장이자 공동 제1저자로 연구 설계와 구현, 평가를 이끌었습니다.

문제

내용

디지털 신원 표준은 데이터 모델과 발급, 제시 절차를 정의하지만 보안 점검에 필요한 기록은 정하지 않습니다.

대상 기술
디지털 신원은 발급자, 지갑을 가진 소지자, 검증자가 자격증명을 주고받는 기술입니다.
기존 분류체계
MITRE ATT&CK은 웹2 환경의 공격 행위를 기준으로 만들어져 디지털 신원의 위협을 다루기에 부족했습니다. 위협 21개를 대조했을 때 다섯 요소가 모두 일치한 것은 6개였습니다.
흩어진 기록
보안 검사 결과와 최종 결정이 여러 구성요소에 나뉘어 남고 구현체마다 남는 정보가 다릅니다.

접근

내용

표준과 공개 구현체에서 위협과 필요한 보안 정보를 식별해 공통 스키마로 정의하고, 그 스키마로 실행 중에 위협을 판정했습니다.

위협 식별
W3C와 OpenID 표준, 보안 권고에서 위협 21개를 정의하고 공개 구현체 15개에서 위협별로 필요한 보안 필드가 기록으로 남는지 확인했습니다.
공통 스키마
구현체마다 다른 기록을 필요했던 검사, 수행된 검사와 결과, 최종 결정으로 나눠 적는 공통 보안 이벤트 스키마로 정의했습니다.
런타임 판정
스키마로 바꾼 기록을 이전 요청과 연결해 위협의 성립 여부를 판정하고, 필요한 값이 없는 실행은 정보 부족으로 따로 남깁니다.
역할
4인 연구팀의 팀장이자 공동 제1저자로 설계와 구현, 평가를 이끌었습니다.

결과

내용

추가 발급 448개를 조건 성립 208개와 정보 부족 240개로 구분했습니다.

조합 분석
위협과 구현체 조합 315개 중 적용되는 164개는 모두 기본 기록만으로 정보가 부족했습니다.
비교 방식
이전 요청 이력을 쓰지 않는 방식은 추가 발급 448개를 하나도 확인하지 못했습니다.

한계와 다음

내용

설계한 다섯 조건 중 세 조건만 평가했으므로 탐지 정확도를 주장하지 않습니다.

평가 범위
고정한 버전의 두 발급자에서 통제한 실험이며 운영 환경에 적용한 결과는 아닙니다.
처리 비용
기록과 판정을 켠 조건은 초당 8건, 끈 조건은 초당 11건에서 포화 지점에 도달했습니다.
다음
다섯 조건 전체를 실제 배포 환경에서 평가할 필요가 있습니다.

실무 활용

내용

디지털 신원 기술을 도입할 때 사고 이후 설명에 필요한 기록이 남는지 점검하는 데 쓸 수 있습니다.

활용 장면
인증이 성공했다는 결과만 남아 어떤 검사가 수행됐는지 확인할 수 없을 때입니다.
활용 방법
위협별로 필요한 기록 목록을 기준 삼아 제품이 실제로 남기는 기록과 대조합니다.
작업 기록 전체 보기
기술 스택
Python 3.12 / Pydantic / JSON Schema 2020-12 / walt.id, Credo TS 연동 코드(Kotlin, TypeScript) / OpenID4VCI, OpenID4VP, W3C DID와 VC 표준 문서 분석
해결해야 한 문제
디지털 신원 표준은 데이터 모델과 발급, 제시 절차를 정의하지만 보안 점검에 필요한 기록은 정하지 않습니다. 인증의 최종 결과만 남는 기록으로는 어떤 검사가 수행됐고 위협이 성공했는지 확인할 수 없습니다. 보안 검사 결과와 최종 결정이 여러 구성요소에 나뉘어 남고, 구현체마다 남는 정보와 위치가 다릅니다. 공개 에이전트 ACA-Py에서는 증명 검증 결과가 최종 검증 값에 반영되지 않는 결함(CVE-2024-21669)이 보고됐습니다. 최종 결과만 남으면 이런 중간 검사 실패를 확인하기 어렵습니다. 같은 증명을 다시 쓰는 공격은 이전 요청과 현재 요청을 연결하는 정보가 있어야 판정할 수 있습니다.
왜 이 문제였나
웹2 환경을 기준으로 만든 분류체계와 범용 로그 형식만으로는 디지털 신원의 위협을 점검하기에 부족했습니다. ATT&CK, CWE 같은 분류체계는 위협의 목적과 행위를 설명합니다. 특정 실행이 성공했는지 가리는 값과 정책, 최종 결과는 규정하지 않습니다. OpenTelemetry, OCSF 같은 형식은 기록의 틀을 제공합니다. 위협별로 꼭 필요한 값과 그 값을 만드는 주체는 따로 정의해야 합니다. 표준에 검사 절차가 있다는 것과 그 검사가 실제로 수행돼 최종 결정에 반영됐다는 것은 다릅니다. 이 간격을 메우는 정의가 필요했습니다.
목표
보안 점검에 쓸 수 있는 이벤트 스키마를 공통 기준으로 제안하고, 그 스키마를 쓰는 런타임 판정 프레임워크로 확인하는 것이 목표였습니다. 위협의 성공 조건을 실행 중에 얻는 정보, 그 정보를 만드는 구성요소, 사건 사이의 관계로 구체화합니다. 15개 구현체에서 그 정보를 어디까지 얻을 수 있는지 확인합니다. 조건 불성립과 정보 부족을 구분하는 판정 구조를 만들고, 판정 범위와 재사용 범위, 처리 비용을 평가합니다.
검토한 방법
기존 분류체계에 대응시키는 것만으로는 실행 판정 조건을 정할 수 없었습니다. 21개 위협을 공격 목적, 사전 조건, 대상, 작동 방식, 성공 결과의 다섯 요소로 정의하고 네 분류체계와 대조했습니다. ATT&CK에서는 다섯 요소가 모두 일치하는 위협이 6개, 부분 일치 5개, 유사 7개, 대응 항목 없음이 3개였습니다. 모두 일치하는 경우에도 실제 판정에는 비교할 대상과 사건 관계를 따로 정해야 했습니다. 기존 연구는 보안 속성을 규칙과 상태로 바꾸는 방법을 보여줍니다. 필요한 정보가 구현체에 없을 때 판정이 무엇을 뜻하는지는 다루지 않았습니다.
선택한 방법
구현체마다 다른 기록을 같은 뜻의 공통 기록으로 바꾸고, 이전 사건과 연결해 판정합니다. 필요했던 검사, 실제 수행된 검사와 결과, 최종 결정을 나눠 적습니다. 각 값이 어디에서 왔는지도 함께 남기고, 원본에 없는 값은 추정하지 않습니다. 재사용 횟수나 이전 처리 결과처럼 여러 요청에 걸친 조건은 규칙이 허용한 범위에서만 사건을 연결해 계산합니다. 입력 거부, 판정기 오류, 위협 성립, 정보 부족, 필수 검사 위반, 조건 불성립으로 나눕니다. 필요한 값이 없으면 정상으로 보지 않고 정보 부족으로 남깁니다. 증명과 자격증명, 접근 토큰의 원문은 저장하지 않고 범위가 제한된 참조값만 비교에 씁니다. T-DID는 발급과 검증 경로 밖에서 동작하며 제품의 결정을 바꾸지 않습니다.
구현
정적 분석은 15개 구현체 전체, 실제 연동은 두 발급자와 한 개의 추가 사례에 한정했습니다. 발급자, 지갑, 검증자 등 역할이 다른 공개 구현체 15개의 버전을 고정하고, 필요한 값이 코드의 어디에서 만들어지고 기본 기록에 남는지 확인했습니다. 입력 검증, 정책, 상태 관리, 규칙 평가, 판정 기록을 모듈로 나눴습니다. 같은 요청의 재시도가 새 발급으로 세어지지 않도록 상태 갱신 조건을 따로 정했습니다. 발급 요청에 붙는 키 소유 증명을 다시 써서 자격증명을 추가로 받는 위협을 walt.id와 Credo TS 두 발급자에 연동했습니다. 검증자에게 보내는 제시 응답을 공격자 세션에 연결하는 세션 고정 위협을 Credo TS와 통제된 연동 앱으로 구성했습니다. 나머지 13개 구현체에는 연동을 만들지 않았습니다.
어려움
같은 의미의 정보가 구현체마다 다른 곳에서 만들어졌고, 설계한 조건 전부를 평가 입력에 담지 못했습니다. walt.id는 증명 검증과 발급 결과를 서로 다른 클래스에서, Credo TS는 한 서비스 안의 다른 구간에서 처리했습니다. 21개 위협 중 10개는 한 운영 주체 안에서 판정 정보를 완성할 수 없어 다른 구성요소의 정보가 필요했습니다. 증명 재사용 위협은 다섯 조건으로 설계했지만, 주 평가 입력에는 같은 증명인지와 증명이 유효했는지에 해당하는 값을 넣지 못했습니다.
해결
설계한 범위와 실제로 평가한 범위를 구분해 보고했습니다. 주 평가는 허용 횟수 초과, 추가 발급, 최종 발급의 세 조건만 계산했고, 결과도 "평가한 조건의 성립"으로만 적었습니다. 허용 횟수를 1로 고정해 허용 횟수 초과와 추가 발급은 같은 자료에서 나옵니다. 서로 독립적인 시험이 아니라는 점을 함께 밝혔습니다. Credo TS 통제 실험에서 결과 확인 단계를 통과하지 못한 제품 결과 3건은 정상이나 탐지 실패로 바꾸지 않고 미확정으로 남겼습니다.
정량 결과
이력과 추가 정보를 함께 쓰자 조건 성립, 조건 불성립, 정보 부족이 구분됐습니다. 151개는 위협이 해당 구현체에 적용되지 않았고, 적용되는 164개는 모두 기본 기록만으로는 정보가 부족했습니다. 통제된 실행 평가를 설계할 수 있는 조합은 22개, 정보나 결과 확인 경로가 부족한 조합은 142개였습니다. 이력을 쓰지 않는 비교 방식은 추가 발급 448개를 하나도 확인하지 못했습니다. T-DID는 208개를 조건 성립, 240개를 정보 부족으로 구분했고 정상 실행 212개는 불성립 210개와 정보 부족 2개였습니다. 시간적으로 분리한 실행에서도 추가 발급 70개는 조건 성립, 80개는 정보 부족으로 나뉘었습니다. 정상 실행 70개에서는 조건 성립이 나오지 않았습니다. walt.id는 개발 로그만으로 15개 모두 정보 부족이었고, 정보를 추가하자 성립 3개와 불성립 12개로 나뉘었습니다. Credo TS는 15개 중 3개가 제품 결과 미확정, 나머지는 성립 3개와 불성립 9개였고, 세션 고정 사례 12개도 성립 3개와 불성립 9개였습니다.
목표 달성
판정 구분은 평가 범위 안에서 확인했고, 처리 비용은 제안 조건이 더 컸습니다. 초당 1건부터 18건까지 13개 부하를 10회씩 측정했습니다. 제안 로깅과 판정을 켠 조건은 초당 8건, 끈 조건은 초당 11건에서 포화 기준에 처음 도달했습니다. 포화 이후 처리량은 초당 약 6~7건과 약 9건이었습니다. 고부하 구간의 메모리는 약 190 MiB와 약 65~70 MiB였습니다. 다섯 조건 중 세 조건만 평가했으므로 탐지 정확도를 주장하지 않습니다. 이력 사용과 정보 부족 처리의 효과를 따로 분리한 결과도 아닙니다. 제품과 분리된 단일 프로세스 실험 환경의 값이며 실제 서비스의 최대 처리량으로 일반화하지 않습니다.
기여
위협의 정의에서 판정 기록까지를 하나의 기준으로 연결했습니다. 4인 연구팀의 팀장이자 공동 제1저자로 연구 설계와 프로토타입 구현, 평가를 이끌었습니다. 표준과 보안 권고에서 21개 위협을 다섯 요소로 정의하고 네 분류체계와의 대응을 분석했습니다. 315개 조합에서 판정 정보를 어디까지 얻을 수 있고 실행 평가가 가능한지 분석했습니다. 같은 위협의 두 발급자 연동은 430줄과 456줄 중 333줄을 공유했습니다. 다른 위협의 연동 547줄에서는 공통 판정 코어 50줄만 그대로 쓰였습니다.
배운 점
위협을 분류하는 일과 실행에서 성공 여부를 판정하는 일은 서로 다른 정보를 요구했습니다. 성공 조건뿐 아니라 그 값을 누가 만드는지, 어떤 사건끼리 연결하는지, 값이 없을 때 무엇으로 기록할지를 같이 정해야 했습니다. Credo TS는 기존 API와 콜백만 허용해도 추가 정보 조건과 같은 결과가 나왔습니다. 특정 로그 형식보다 필요한 정보를 믿을 수 있는 경로에서 얻는 것이 중요하다고 느꼈습니다.
한계
고정한 버전과 통제된 실험 범위의 결과이며 일반화하지 않습니다. 15개 구현체는 역할의 다양성을 보고 고른 표본입니다. 315개 조합의 분포는 취약점 비율이나 제품별 보안 수준을 뜻하지 않습니다. 주 평가는 한 위협의 세 조건이고, 통제 사례는 소규모여서 정밀도나 공격 탐지율(재현율)을 추정하지 않습니다. 같은 절차를 시간만 분리해 반복한 것이어서 다른 배포 환경에서도 같다는 근거는 아닙니다. 기록을 만드는 쪽이 실제 처리와 일치하게 기록한다고 가정합니다. 허위 기록이나 사건 은폐는 검증하지 못합니다.
후속 연구
증명 재사용 위협의 다섯 조건 전체와, 여러 구성요소의 정보가 필요한 위협을 실제 배포 환경에서 평가할 필요가 있습니다. 이력 유지와 정보 부족 처리의 효과도 분리해 측정해야 합니다.
조직에서 내리는 판단
고객이나 임직원의 디지털 신원을 서비스에 쓸 때는 인증이 성공했다는 결과만으로는 사고 이후의 설명이 어렵습니다. 어떤 검사가 수행됐고 최종 결정이 무엇이었는지를 사건 단위로 남기고, 기록이 부족한 실행을 정상으로 분류하지 않는 기준이 필요하다고 판단했습니다. 이 연구에서는 그 기준을 위협별로 정의하고 두 개의 공개 구현체에서 직접 확인했습니다. 현재 결과는 통제된 실험 범위이며 운영 환경에 적용한 결과는 아닙니다.
