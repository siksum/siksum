JOIN

버전과 분석 환경이 다른 외부 컨트랙트를 같은 절차로 검토하는 Python CLI입니다.

2023.03–2023.06
Hanwha Life DREAMPLUS × Theori
역할
DREAMPLUS Academy 2nd 프로젝트 멤버, Static Analysis Development 담당

개요

버전과 구조가 제각각인 외부 컨트랙트를 같은 명령으로 컴파일하고 점검하는 Python 명령줄 도구입니다.

역할

정적 분석 개발 담당으로 컴파일러 자동 전환, 탐지 규칙 추가와 삭제, 업무 로직 점검을 구현했습니다.

문제

내용

외부에서 가져온 스마트 컨트랙트는 같은 기준으로 반복해서 검토하기 어려웠습니다.

실행 조건
컨트랙트마다 언어 버전과 폴더 구조가 달라 분석 도구의 설정을 매번 다시 해야 했습니다.
업무 로직
기존 도구는 알려진 취약 패턴만 찾고 자금과 권한 로직이 의도대로인지는 확인하지 못했습니다.

접근

내용

규칙을 추가할 수 있는 공개 분석 도구 Slither 위에 명령줄 도구를 만들었습니다.

내 역할
정적 분석 개발 담당으로 컴파일러 자동 전환, 탐지 규칙 관리, 업무 로직 점검을 구현했습니다.
컴파일
코드에 적힌 버전 조건을 읽어 맞는 컴파일러를 자동으로 설치하고 전환합니다.
업무 로직
원본 Uniswap V2와 비슷한 함수를 찾아 유동성 공급 단계가 유지됐는지 확인했습니다.

결과

내용

84개 규칙을 골라 실행하게 했고, Slither와의 비교 결과는 규칙마다 엇갈렸습니다.

구현 범위
기본 규칙 84개의 선택 실행에 탐지 패턴 7개와 업무 로직 점검 1개를 더했습니다.
유리한 결과
발신자 확인 오류 143건에서는 137건을 찾아 Slither의 58건보다 많았습니다.
불리한 결과
정수 넘침 97건에서는 오탐이 90건이었고, 강제 송금 152건에서는 Slither보다 39건 적게 찾았습니다.

한계와 다음

내용

코드 유사도와 정해진 규칙만으로는 컨트랙트의 위험을 다 판단하지 못합니다.

한계
비교 평가의 정답 기준 기록이 없어 전체 정확도로 일반화하지 않고, 화면 연동도 끝내지 못했습니다.
다음
이 한계가 코드 유사성 연구와 실제 거래의 의미를 복원하는 DeFiSense로 이어졌습니다.

실무 활용

내용

외부 컨트랙트를 도입하기 전에 같은 기준으로 1차 선별하는 데 쓸 수 있습니다.

활용 장면
협력사나 오픈소스 컨트랙트의 버전과 구조가 제각각일 때입니다.
활용 방법
같은 명령으로 점검하고, 원본과 달라진 함수를 찾아 추가 검토 대상을 좁힙니다.
주의할 점
규칙을 통과했다고 해서 승인으로 보지 않습니다.
작업 기록 전체 보기
기술 스택
Python 3.8+ / CLI / Slither / Crytic Compile / solc-select / Solidity AST / CFG / SlithIR / custom detector / fastText / NumPy / Euclidean distance / tabulate / Etherscan 공개 컨트랙트 테스트 케이스
해결해야 한 문제
외부 컨트랙트는 실행 조건이 제각각이었고, 기존 도구로는 업무 로직을 확인하기 어려웠습니다. 외부 스마트 컨트랙트는 Solidity 버전과 프로젝트 구조가 달라 같은 분석 도구로도 실행 조건이 달라졌습니다. 기존 정적 분석기는 알려진 취약 패턴에는 강했습니다. 하지만 프로토콜마다 다른 자금과 권한 로직이 의도대로 구현됐는지는 확인하기 어려웠습니다.
왜 이 문제였나
수동 검토와 자동 도구 모두 같은 품질로 반복하기 어려웠습니다. 시간과 전문가 경험에 따라 품질 편차가 생깁니다. 설치와 규칙 주입에 별도 학습이 필요했습니다. 반복 가능한 1차 검토 절차와 업무 로직을 점검할 실험 경로가 필요했습니다.
목표
여러 형태의 입력을 같은 CLI로 컴파일하고 점검하는 분석 도구를 만들기로 했습니다. 파일, 디렉터리, ZIP 입력을 같은 CLI로 컴파일합니다. 탐지 규칙, 코드 유사도, 업무 로직 점검을 선택적으로 실행합니다.
검토한 방법
기존 분석 도구 네 가지와 분석 방식의 장단점을 비교했습니다. Slither, Mythril, Securify, Solhint를 탐지 방식, 사용자 정의 규칙, 유지보수성과 실행 환경 기준으로 비교했습니다. 기호 실행, Datalog, AST 패턴과 SlithIR 기반 정적 분석의 장단점을 검토했습니다.
선택한 방법
확장 규칙을 만들 수 있는 Slither를 기반으로 선택하고 업무 로직은 2단계로 확인했습니다. AST, CFG, SlithIR과 Python API를 제공하고 확장 규칙을 만들 수 있는 Slither를 선택했습니다. SolcParser로 자동화했습니다. 함수 유사도로 후보를 찾은 뒤 별도 규칙으로 업무 로직을 확인합니다.
구현
dream CLI 하나에 컴파일러 관리, 규칙 기반 탐지, 업무 로직 점검을 넣었습니다. 버전 확인, ruleset 추가와 삭제, 취약점과 로직 및 전체 탐지, 유사도 학습과 검사 명령을 구성했습니다. pragma의 <, >, ^, ~, = 조건을 해석해 컴파일러 설치와 전환을 자동화했습니다. 단일 파일, 디렉터리, ZIP 입력을 처리합니다. 전체, 분류, 개별 detector를 선택해 실행할 수 있게 했습니다. Uniswap V2의 addLiquidity와 addLiquidityETH 유사 함수를 찾습니다. 최적 수량 계산과 자산 전송 단계가 유지되는지 확인했습니다.
어려움
경계 입력에서 오류가 났고 업무 로직을 하나의 규칙으로 일반화하기 어려웠습니다. 문법 오류가 파일 형식 오류로 표시되거나 하위 디렉터리의 같은 이름 파일을 구분하지 못하는 문제가 있었습니다. 파생 프로토콜마다 로직이 달라 AMM과 선물 로직을 하나의 규칙으로 일반화하기 어려웠습니다.
해결
입력 경로를 하나로 묶고 업무 로직은 확인 가능한 범위로 제한했습니다. 컴파일과 분석 단계를 감싼 공통 입력 경로를 만들었습니다. 규칙 파일과 import 경로의 추가와 삭제를 자동화했습니다. 업무 로직은 전 범위를 단정하지 않고 유사 함수 후보를 먼저 좁힌 뒤 확인 가능한 두 함수로 범위를 제한했습니다.
정량 결과
84개 규칙을 선택 실행할 수 있게 했고, 기존 도구와의 비교 결과는 엇갈렸습니다. 11개 분류의 84개 Slither 규칙을 선택 실행할 수 있게 했습니다. 84개는 Slither의 기본 규칙이고 팀이 한 일은 분류와 선택 실행이며, 여기에 7개 탐지 패턴과 1개 Uniswap V2 유동성 공급 로직 점검을 더했습니다. 팀에서 Etherscan에서 모은 테스트 케이스로 규칙별로 Slither, Mythril과 비교했습니다. tx.origin 143건에서는 미탐 0, 정탐 137, 오탐 5건으로 Slither(미탐 85, 정탐 58)보다 많이 찾았습니다. over/underflow 97건에서는 오탐이 90건이었습니다. Forced Ether Send 152건에서는 정탐이 49건으로 Slither의 88건보다 적었습니다. 정답 기준 기록이 남아 있지 않아 전체 정확도로 일반화하지 않습니다.
목표 달성
반복 가능한 CLI와 핵심 분석 기능은 구현했고 일부는 완료 범위 밖으로 남았습니다. 반복 가능한 CLI와 핵심 분석 기능을 구현했습니다. 프런트엔드 연동, 파생 프로토콜 전반의 업무 로직 일반화, 경계 입력 처리는 완료 범위 밖으로 남았습니다.
기여
정적 분석 개발 담당으로 Slither의 흐름을 분석하고 핵심 경로를 구현했습니다. Static Analysis Development 담당으로 Slither의 컴파일, 중간표현, 탐지 흐름을 분석했습니다. SolcParser와 규칙 관리, detector 실행, 업무 로직 점검 경로를 구현했습니다.
배운 점
이름과 구조가 유사하다고 경제적 기능까지 같지는 않습니다. 코드 후보를 빠르게 좁히는 기술과 실제 자금 이동과 상태 변화가 의도와 맞는지 확인하는 기술은 분리해야 한다는 점을 확인했습니다.
한계
유사도와 정적 규칙만으로는 위험을 완전히 판단하지 못합니다. 유사도 임계값 0.95와 정적 규칙은 알려진 코드 계열을 찾는 데 유용합니다. 프록시, 외부 호출, 오라클, 거래 순서가 만드는 위험은 완전히 판단하지 못합니다.
후속 연구
입력 처리를 보완하고 코드 분석 결과를 온체인 증거에 연결해야 합니다. 컴파일 오류 분류와 경로 충돌을 보완해야 합니다. 코드 분석 결과를 온체인 호출과 자금 흐름 증거에 연결해야 합니다. 이 한계가 이후 코드 유사성 연구와 DeFiSense의 거래 의미 복원으로 이어졌습니다.
조직에서 내리는 판단
협력사나 오픈소스 컨트랙트를 도입할 때 서로 다른 버전을 같은 기준으로 1차 선별하고, 권한 / 자금 함수와 원본 대비 변경 지점을 검토하는 용도로 연결할 수 있습니다. 규칙 통과를 승인으로 간주하지 않고 추가 검토가 필요한 계약을 좁히는 통제 단계입니다.
